### Bridge compute shape (TWIL-02)

- **D-56 (REVISED 2026-05-07): Bridge = AWS App Runner service with `min-instances=0` (scale-to-zero).** Researcher (`06-RESEARCH.md` Q1, dated 2026-05-07) demonstrated that the original Lambda + API Gateway WebSocket architecture cannot work: APIGW WS integration timeout is 29s and Lambda is stateless, so a single invocation cannot hold an upstream Bedrock-AgentCore WSS open for the duration of a phone call (DynamoDB cannot serialize a live socket; per-frame fresh sessions break Sonic's bidi-stream contract; no canonical AWS sample exists for the chain `Twilio → APIGW WS → Lambda → AgentCore Runtime`). App Runner with `min-instances=0` is the smallest-blast-radius fix: a long-running Python FastAPI container that holds the per-call upstream WSS in process. Cost shape preserves the demo-budget rule that drove the original Lambda choice — App Runner with `min=0` is **$0/mo idle** (scale-to-zero); only burns ~$0.005/vCPU-min during active calls. Twilio inbound (~$1/mo number hold + ~$0.013/min US/CA) and AgentCore Bedrock spend are unchanged. Alternatives rejected: Lambda + APIGW WS (structurally cannot work — Q1 finding); Fargate behind ALB (~$15-30/mo idle even with min-tasks=0, plus VPC re-introduction); reusing the existing `hera-agent` ECR image as the bridge (conflates agent and bridge — v2 deploy failure could break v1 image roll-back path); Pipecat `[twilio]` extra + TwilioFrameSerializer (heavier dependency tree than the bridge needs; bridge is a thin frame translator, not a full Pipecat pipeline). The planner researches and confirms App Runner's exact `min-instances=0` configuration semantics before locking the Terraform shape.
- **D-57 (REVISED 2026-05-07): Bridge App Runner service lives in a NEW Terraform module `infra/modules/twilio_bridge/`.** This is NOT a sibling of `widget_presigner/` in shape (widget_presigner is a Lambda + Function URL module); the new module has the App Runner shape: `aws_apprunner_service` (with `instance_configuration { instance_role_arn = ... }`, `source_configuration { authentication_configuration { access_role_arn = ... } image_repository { ... } }`, `network_configuration { ingress_configuration { is_publicly_accessible = true } }`, `auto_scaling_configuration_arn` referencing a configuration with `min_size = 0`/`min_instances = 0`), `aws_iam_role` instance role for the bridge container's runtime AWS credentials (granting `bedrock-agentcore:InvokeAgentRuntimeWithWebSocketStream` on the live runtime ARN), `aws_iam_role` access role for App Runner to pull from ECR, `aws_ecr_repository` `hera-twilio-bridge` with `image_tag_mutability = IMMUTABLE` and `image_scanning_configuration.scan_on_push = true` (mirrors Phase 3 `hera-agent` ECR shape), `aws_cloudwatch_log_group` `/aws/apprunner/hera-twilio-bridge-prod` with retention 7 days. Module file layout: `versions.tf` / `variables.tf` / `main.tf` / `iam.tf` / `outputs.tf` + `src/` (Python FastAPI bridge code) + `Dockerfile`. Reason: keeping the bridge in its own module preserves single-responsibility — v2 deploy failure cannot break v1 widget_presigner. Cleanup-verify-twilio.sh asserts only v2 resources gone (App Runner service + bridge ECR + bridge IAM roles + bridge log group); widget_presigner is explicitly NOT in its leftover list.
- **D-58 (REVISED 2026-05-07): Upstream WSS persistence is in-process per-call coroutine inside the App Runner container.** The bridge handler is a long-lived Python process; for each incoming Twilio Media Streams WebSocket (one per phone call), the handler spawns an asyncio coroutine that opens a SigV4-signed upstream WSS to `wss://bedrock-agentcore.ap-northeast-1.amazonaws.com/runtimes/<URL-ENC-ARN>/ws?qualifier=DEFAULT` with the Twilio CallSid as `X-Amzn-Bedrock-AgentCore-Runtime-Session-Id`, holds it open for the call duration, bidirectionally bridges resampled audio, and closes both ends on the Twilio `stop` event or peer hang-up. No DynamoDB, no `/tmp` warm-state, no API Gateway routing tables — App Runner's persistent process model makes this trivial. Sonic 8-min stream cap (Phase 2 D-19, AGT-05) interaction: the unchanged agent's `SessionContinuationParams(transition_threshold_seconds=360)` rotates the bidi stream inside the AgentCore Runtime; the bridge sees this as a normal Sonic event and does not need to handle stream rotation. App Runner's per-instance max-concurrency (planner picks; e.g., 5 to bound cost) is sized below the upstream AgentCore concurrency cap=2 (D-30) so the bridge cannot fan-out beyond what AgentCore accepts.

### Audio resample location (TWIL-01)

- **D-59 (REVISED 2026-05-07 — body unchanged except for compute target): μ-law 8 kHz <-> Int16 16 kHz resample lives ENTIRELY inside the bridge App Runner container.** Inbound Twilio media frames are decoded from base64 + μ-law -> Int16 + upsampled 8kHz -> 16kHz before forwarding to AgentCore upstream WSS; outbound Sonic Int16 frames are downsampled to 8kHz + encoded to μ-law + base64 + wrapped in Twilio media event before write to the Twilio WS. Agent code, container image, and AgentCore Runtime are NOT modified — v1 contract preserved. Resample lib resolved: **Python 3.13 + `audioop-lts==0.2.x` PyPI shim** (per `06-RESEARCH.md` Q2). The shim is a verbatim drop-in for Python 3.12 stdlib `audioop` (removed in 3.13 via PEP 594), provides `lin2ulaw` / `ulaw2lin` / `ratecv` with identical signatures, weighs 24-104 KB, and has negligible cold-start impact. **Open caveat that planner must address**: the exact Sonic output sample rate over `bedrock-agentcore /ws` is not yet probed live — Phase 2 RUNBOOK says Pipecat default OUT is 24 kHz Int16 (AGT-07), but at the AgentCore data-plane WSS the framing may differ. Planner adds a Wave-1 task to probe the live Runtime, capture one outbound frame, log its sample rate, and adjust the resampler `inrate` parameter accordingly (`16000` or `24000`). Without this verification, the SC#2 "no chipmunk effect" gate may fail. `audioop.ratecv` filter state must be threaded across frames within a call (lives in the per-call coroutine's local scope — App Runner persistence makes this trivial; Lambda-fresh-state was a separate problem solved by the D-56 revision).

### Integration Points (REVISED 2026-05-07 for App Runner shape)
- **Twilio -> App Runner FastAPI -> in-process AgentCore client** — Twilio dials the configured number; voice webhook returns the TwiML Bin XML which contains `<Connect><Stream url="wss://${apprunner_url}/twilio"/>`; Twilio opens a WebSocket directly to the App Runner public hostname; App Runner FastAPI handler accepts the upgrade, validates `X-Twilio-Signature` HMAC once, parses Twilio events (`connected`/`start`/`media`/`stop`/`mark`/`dtmf`) inline, opens an upstream WSS to AgentCore for the call duration, and bridges audio frames bidirectionally with resample.
- **Bridge App Runner -> AgentCore Runtime** — for each accepted Twilio call, the bridge handler opens a SigV4-signed upstream WSS to `wss://bedrock-agentcore.ap-northeast-1.amazonaws.com/runtimes/<URL-ENC-ARN>/ws?qualifier=DEFAULT` with the Twilio CallSid as `X-Amzn-Bedrock-AgentCore-Runtime-Session-Id` (or as `?session_id=...` query param), holds it open for the call, and closes both ends on Twilio `stop` / peer hang-up. This is the SAME upstream the widget uses (via the presigned URL); Phase 6's bridge signs server-side instead of minting a URL for the browser.
- **AgentCore concurrency cap=2** (D-30) is the SHARED upstream budget for browser + phone — a phone call competes with browser sessions for one of the 2 slots. RUNBOOK documents this interaction. App Runner's `max_instances` is set to 2 (matching the upstream cap) so the bridge cannot fan out beyond what AgentCore accepts.
- **App Runner cold start + Twilio handshake timing** — App Runner with `min-instances=0` has a cold start (~1-3s for a small Python container per AWS docs; planner verifies). Twilio's TCP/TLS handshake to the bridge tolerates this; the upstream WSS open to AgentCore happens after the Twilio `start` event so it doesn't add to the call-pickup latency budget. SC#1 ("3 seconds of first sentence") covers from utterance to audible response, which is dominated by Sonic + KB latency, not by App Runner cold start.
