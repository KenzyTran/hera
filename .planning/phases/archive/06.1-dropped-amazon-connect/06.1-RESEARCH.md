# Phase 6.1: Native AWS Voice Channel — Amazon Connect - Research

**Researched:** 2026-05-16
**Domain:** Amazon Connect + Lex V2 + Lambda + Bedrock KB Retrieve cross-region; PSTN inbound voice on AWS-native stack
**Confidence:** HIGH on every locked Terraform/runtime fact; MEDIUM on first-time-account behavior (depends on whether the SLR is auto-created); the one architectural reconciliation point flagged below

## Summary

Phase 6.1 is mostly feasible end-to-end on the locked Terraform `~> 6.27` stack (lockfile 6.43.0/6.45.0). The Bedrock-KB-Retrieve cross-region path, the Connect-side `aws_connect_instance` + `aws_connect_phone_number` + `aws_connect_contact_flow` resources, the five `aws_lexv2models_*` resources for the bot/locale/intent/version, and the Lambda packaging shape all exist and align with CONTEXT.md / SPEC.md.

**One hard architectural reconciliation point surfaces from the research:**

1. **`aws_lexv2models_bot_alias` does NOT exist** as of provider v6.45.0 (2026-05-13). The 5-resource minimum named in D-68 is currently a 4+1 split: 4 native `aws_lexv2models_*` resources for bot + locale + intent + version, plus the alias must come from `awscc_lex_bot_alias` (Cloud Control provider, latest v1.84.0, 2026-05-13) OR a `null_resource` + `aws lexv2-models create-bot-alias` shim. Both are battle-tested community workarounds; `awscc_lex_bot_alias` is the cleaner choice (declarative, drift-aware, no shell).

2. **`aws_connect_bot_association` is Lex V1 only.** The Lex-V2 association path is Connect's `AssociateBot` API (V1+V2-compatible). There's no Terraform resource that wraps `AssociateBot` for V2. The supported workaround documented by AWS itself is to **set the bot alias ARN manually in the Contact Flow JSON** and add a resource-based policy to the Lex V2 bot alias granting `connect.amazonaws.com` access — which `awscc_lex_resource_policy` ships as a first-class resource.

3. **`$.External.message` in D-69 is incorrect for Connect <-> Lex V2 data passing.** The canonical Connect JSONPath to read a Lex V2 session attribute that the Lambda set is `$.Lex.SessionAttributes.<key>` (see `Amazon Lex contact attributes` table in Connect docs). `$.External.*` is the path for `Invoke AWS Lambda function` block return values (different block, different path). The Lambda still needs to do the work — it sets the answer string into `sessionState.sessionAttributes` in its Lex V2 response, and Connect's `Play Prompt` block reads it via `$.Lex.SessionAttributes.answer` (planner picks key name). The Lambda's `messages[*].content` is what Lex itself plays back to Connect for any direct utterance turn, but for a "Lambda computes answer, Connect plays it" one-shot pattern the sessionAttributes path is the standard. Reconciliation: D-69 needs to be re-validated with the user as a follow-up discuss-phase question OR the plan can lock the `$.Lex.SessionAttributes.answer` shape and document the reconciliation as a researcher correction.

**Primary recommendation:** Lock the plan around: 4 `aws_lexv2models_*` resources + 1 `awscc_lex_bot_alias` + 1 `awscc_lex_resource_policy` (granting Connect access to the alias) + `aws_connect_instance` + `aws_connect_phone_number` + `aws_connect_contact_flow` (with Lex V2 bot alias ARN injected via `templatefile`) + `aws_lambda_function` + `aws_lambda_permission` for `lexv2.amazonaws.com` source-arn-scoped to the bot alias ARN. Use sessionAttributes for Connect<->Lambda data passing; the `messages[*].content` Lex returns is the literal TTS text Lex plays back. Skip `aws_connect_bot_association` entirely.

## Architectural Responsibility Map

| Capability | Primary Tier | Secondary Tier | Rationale |
|------------|-------------|----------------|-----------|
| PSTN ingress (DID + telephony) | Amazon Connect (managed) | — | Free tier covers US/CA inbound; no self-managed telco stack. |
| TTS synthesis to caller | Polly via Connect Set Voice / Play Prompt | — | Connect-bundled, no per-call IAM grant from user side. |
| ASR / STT of caller speech | Lex V2 (built into `ConnectParticipantWithLexBot`) | — | Lex's voice-channel ASR feeds `event.inputTranscript`. |
| Intent classification | Lex V2 `AMAZON.FallbackIntent` | — | Single-intent design routes EVERY utterance through Lambda. |
| Business logic + KB retrieval | Lambda (Python, us-east-1) | Bedrock KB Retrieve (ap-northeast-1) | Lambda is the only place running our code. |
| KB vector retrieval | Bedrock KB `BKXE19AH89` (ap-northeast-1, unchanged) | S3 Vectors backend | Reused verbatim from Phase 1; D-64 carry-forward. |
| Response TTS playback | Polly (Connect Play Prompt block reading session attribute set by Lambda) | — | Lambda sets `sessionState.sessionAttributes.answer`; Contact Flow reads via `$.Lex.SessionAttributes.answer`. |
| IAM least-privilege gating | Lambda exec role + AWSServiceRoleForAmazonConnect_<id> + Lex resource-based policy on bot alias | — | Three boundaries: Lambda→KB (consumer policy reuse), Connect→Lex (RBP), Lex→Lambda (`aws_lambda_permission`). |

### Pattern 2: Lambda fulfillment handler (Lex V2 input -> KB Retrieve cross-region -> sessionAttributes response)

```python
# lambda/handler.py
"""Hera voice lookup Lambda.

Lex V2 fulfillment hook for the FallbackIntent of bot hera-product-lookup-prod.
Reads the caller's transcribed utterance from event.inputTranscript, calls the
Bedrock Knowledge Base BKXE19AH89 in ap-northeast-1 cross-region, formats a
one-sentence answer, and returns it both as a Lex V2 message AND as a
sessionAttribute so Connect's Play Prompt block can read it via
$.Lex.SessionAttributes.answer.
"""

import os
import boto3

KB_ID = os.environ["KB_ID"]                  # BKXE19AH89
KB_REGION = os.environ["KB_REGION"]          # ap-northeast-1
NUM_RESULTS = int(os.environ.get("NUM_RESULTS", "3"))

_kb = boto3.client("bedrock-agent-runtime", region_name=KB_REGION)


def _retrieve(query: str) -> str:
    """Call KB Retrieve and return the top-1 document text, or empty string."""
    resp = _kb.retrieve(
        knowledgeBaseId=KB_ID,
        retrievalQuery={"text": query},
        retrievalConfiguration={
            "vectorSearchConfiguration": {"numberOfResults": NUM_RESULTS}
        },
    )
    results = resp.get("retrievalResults", [])
    if not results:
        return ""
    return results[0]["content"]["text"]


def _format_answer(query: str, kb_text: str) -> str:
    """Produce a single sentence containing the product and stock status.

    The KB content is markdown; we look for stock keywords. If nothing matches,
    return a fallback sentence that still names the product the caller asked for.
    """
    lowered = kb_text.lower()
    # The catalog uses "Stock: In stock" or "Stock: Out of stock" markdown fields.
    if "in stock" in lowered:
        status = "in stock"
    elif "out of stock" in lowered:
        status = "out of stock"
    else:
        status = "available"
    # Caller's exact phrasing is preserved as the product noun.
    return f"Yes, {query} is {status}."


def lambda_handler(event, context):
    transcript = event.get("inputTranscript", "").strip()
    if not transcript:
        answer = "Sorry, I could not hear you."
    else:
        kb_text = _retrieve(transcript)
        answer = (
            _format_answer(transcript, kb_text)
            if kb_text
            else f"Sorry, I do not have information about {transcript}."
        )

    intent_name = event["sessionState"]["intent"]["name"]
    return {
        "sessionState": {
            "dialogAction": {"type": "Close"},
            "intent": {"name": intent_name, "state": "Fulfilled"},
            "sessionAttributes": {"answer": answer},
        },
        "messages": [
            {"contentType": "PlainText", "content": answer},
        ],
    }
```

### Anti-Patterns to Avoid

- **Using `aws_connect_bot_association`.** It is Lex V1 only and AWS deprecated Lex V1 on 2025-09-15 [CITED: docs.aws.amazon.com/connect/latest/adminguide/amazon-lex.html "End of support notice"]. Use `awscc_lex_resource_policy` + manual Contact Flow alias ARN instead.
- **Putting the Lex alias ARN as a static string in the Contact Flow JSON file.** Always inject via `templatefile()` — alias IDs are generated per-apply.
- **Returning the KB answer ONLY in Lex `messages[*].content` and ALSO playing it via Connect Play Prompt.** Caller hears it twice. See Pattern 3 reconciliation note.

- **Setting `min_size=0` on any App Runner ASC.** Phase 6 already proved this fails (AWS rejects). This is Phase 6 history; for 6.1 we're destroying App Runner, not creating, so this is purely an archive-doc concern.

## Common Pitfalls

### Pitfall 1: `aws_lexv2models_bot_version` race with `aws_lexv2models_intent`
**What goes wrong:** Bot version creation is rejected because the locale has no intents OR the intent was created after the version targeted DRAFT. Error: `ValidationException: There are no intents in the locale "en_US" in your bot draft version`.
**Why it happens:** Lex builds the locale at version-create time. The intent must already exist and be valid before the bot_version resource publishes.
**How to avoid:** Use `depends_on = [aws_lexv2models_intent.fallback]` on `aws_lexv2models_bot_version`. Terraform's data-flow dependency detection misses this because the intent and version both reference the bot ID, not each other.
**Warning signs:** First apply fails on version create; second apply (with no code changes) succeeds.

### Pitfall 2: `awscc_lex_bot_alias` requires Lambda ARN at create time
**What goes wrong:** Apply order tries to create the alias before the Lambda exists → invalid Lambda ARN reference.
**Why it happens:** The alias's `bot_alias_locale_settings[].code_hook_specification.lambda_code_hook.lambda_arn` references the Lambda; Terraform should infer the ordering, but the awscc provider sometimes ignores cross-provider deps.
**How to avoid:** Explicit `depends_on = [aws_lambda_function.lookup, aws_lambda_permission.lex_invoke]` on `awscc_lex_bot_alias.prod`. Or split apply into two passes (Lambda first, then Lex alias).
**Warning signs:** First apply fails with `Lambda function not found`; re-apply succeeds.

### Pitfall 3: Lex resource-based policy AWS:SourceAccount + AWS:SourceArn condition required
**What goes wrong:** Calls from Connect to Lex fail with `AccessDeniedException` even though the policy lists the right action.
**Why it happens:** Per AWS docs, "the condition block is required for service principals, and must use the global context keys `AWS:SourceAccount` and `AWS:SourceArn`."
**How to avoid:** Always include both `AWS:SourceAccount` (account-ID string) and `AWS:SourceArn` (the Connect instance ARN, NOT the bot alias ARN) conditions in `awscc_lex_resource_policy.policy`. See Pattern 1 above.
**Warning signs:** CCP smoke fails silently — caller hears greeting, then long silence, then disconnect. CloudWatch Lex logs show `AccessDeniedException`.

### Pitfall 4: Connect service-linked role already exists
**What goes wrong:** `aws_iam_service_linked_role` create fails with `InvalidInput: A service-linked role already exists`.
**Why it happens:** The Connect Console creates the SLR on first instance creation. If the user (or any prior testing) touched the Connect Console even once for this account, the SLR is already there.
**How to avoid:** Skip the `aws_iam_service_linked_role` resource — rely on `aws_connect_instance` to auto-create. OR use a `data "aws_iam_service_linked_role"` + conditional. The simplest path: let Terraform NOT manage the SLR; document in RUNBOOK that the SLR is AWS-managed and operator does not delete it.
**Warning signs:** First apply fails on the SLR resource if Terraform tries to manage it.

### Pitfall 5: First-time DID claim race / Console-only path
**What goes wrong:** `aws_connect_phone_number` create succeeds at the Terraform level but the number is not in CLAIMED status — Connect's eligibility check takes seconds-minutes. OR, in some accounts/regions, AWS rejects the first DID claim until the account has been "verified" for Connect via Console.
**Why it happens:** Connect's phone-number claim API is async and depends on account standing. Most US accounts can claim a DID instantly, but a fresh account may need to use the Console to confirm Connect-instance setup first.
**How to avoid:** RUNBOOK paste-flow includes: (a) verify `aws connect list-instances` shows the new instance ACTIVE before terraform tries to claim DID, (b) if claim fails, fall back to claiming via Console (no Terraform-only path), (c) re-run `terraform apply` to wire the manually-claimed DID via `terraform import aws_connect_phone_number.us_did <number-id>`.
**Warning signs:** `aws_connect_phone_number` reports CLAIMED status but the number is not reachable from a phone within 5 minutes. CCP doesn't show the number in the dropdown.

### Pitfall 6: Lex V2 resource-based policy not cross-region
**What goes wrong:** Bot alias in us-east-1, Connect instance in us-east-1 — works. Bot alias in us-east-1, Connect instance in eu-west-1 — fails.
**Why it happens:** "You can't use cross-account or cross-region policies with Amazon Lex V2" [CITED: docs.aws.amazon.com/lexv2/latest/dg/security_iam_resource-based-policy-examples.html].
**How to avoid:** SPEC.md already locks both in us-east-1 — no risk for v2.0. Document for future regional expansion.

### Pitfall 7: SLR auto-deletes Connect instance metadata on `terraform destroy`
**What goes wrong:** `terraform destroy` of the Connect instance may not fully clean up the SLR or associated phone-numbers state, leading to ghost charges.
**Why it happens:** Connect instance deletion is async — Connect cleans up associated resources on its side, but the SLR remains.
**How to avoid:** RUNBOOK cleanup section documents: (a) `terraform destroy -target=module.aws_voice_channel`, (b) wait 5-10 minutes for Connect to finalize, (c) `aws connect list-instances` confirms zero instances, (d) the SLR is left alone (auto-deleted by AWS when the last instance is gone).

### Pitfall 8: Caller hears the answer twice (Lex's `messages[*].content` + Connect's Play Prompt)
**What goes wrong:** Lambda returns the answer in BOTH `messages[*].content` AND `sessionAttributes.answer`. Lex plays the message, then returns to Connect, which then plays the sessionAttribute via Play Prompt. Caller hears the same answer twice.
**Why it happens:** Lex automatically plays `messages[*].content` on the user-facing side before returning control to the caller channel.
**How to avoid:** Make `messages` a single-space PlainText or omit messages entirely (Lex V2 allows empty messages when `dialogAction.type=Close`); rely on Connect Play Prompt + `$.Lex.SessionAttributes.answer`. See Pattern 3 reconciliation note.
**Warning signs:** During CCP smoke, the answer is spoken twice. Investigate by checking CloudWatch Lex conversation log if enabled.
